## 今回の実装範囲と責務

1. `route-search-model.js`: 地点候補と ID 解決、経由地検証、比較順、次便検索の日時、共有条件の安全な符号化を扱う純粋なモデル。
2. `stop-autocomplete.js`: 検索画面内だけの候補 Controller。IME、Arrow/Enter/Escape、ARIA、候補タップ、選択済み ID の管理。
3. `route-search-ui.js`: 既存フォーム／Worker／Screen adapter を拡張。候補・経由を入力に置き、比較・条件変更・次便を結果に置く。長い詳細をホームへ戻さない。
4. `route-search-view.js`: 既存の候補・経路詳細の描画を Controller から分離。取得済み番線と途中駅を表示。
5. `search-history.js`: 既存形式を互換維持し削除を追加。保存対象は利用者操作のみ。
6. `route-search.css`: 各既存ルールを直接整備し、新しい要素に限定したルールを定義。末尾への大量上書きを行わない。

`idle-experience.js` の既存ホーム簡易検索にも同じ候補 Controller を接続し、機能と外観を維持する。`fast-data.js` の事前取得を検索でも共有し、重複通信を防ぐ（5分 TTL、最大16件、失敗は再試行、キャンセルは他画面の取得を中断しない）。時刻表が揃った時点で候補を先に表示し、実測更新は4秒 timeout で続ける。別の日の検索に現在の実測遅延を流用しない。保存ダイヤへのフォールバックは古い情報として明示する。

新 Navigation は追加しない。検索→結果→詳細、戻る、Swipe、タブ状態保存の既存構造を利用。結果の並べ替えは元の経路 index で参照し、見た目の位置を案内対象に使わない。再検索は結果の request snapshot を使い、別タブで変更した入力に依存しない。

## 追加実測が必要な項目

- 実機 iPhone Safari／ホーム画面 PWA で候補選択・IME・キーボード・Edge Back、100/150/200% の文字サイズ。ブラウザ試験は近似であり実機合格の代用にしない。
- 京都・丸太町・北大路・北3で各5回、入力開始→結果、結果→案内開始の所要時間、操作数、誤選択率。競合アプリと同じ地点・時刻・回線で測定する。
- 平日／休日／学校休校、直通 K/B 境界、上下方向、終電前後の実到着と予測の中央値／95百分位、バスの実測更新間隔と欠測率。
- 下り・上りの番線、出入口、乗換の歩行時間、エレベーター・車椅子対応、混雑データの公式根拠と現地確認。
- cold/warm/offline 検索の性能、弱い回線での中断／再試行、画面復帰時の無駄な通信。

操作の改善は今回実装するが、全国／世界のデータ網羅性やサービス全体が競合以上になったと断定しない。取得できない交通データを UI の追加だけで解決した扱いにはしない。

## 実装後の Navigation と機能保存

```
今（簡易検索・最近・近く）／時刻表
  → 経路検索（交通機関別候補、経由・滞在、日時・条件）
    → 検索結果（到着／料金／乗換順、条件変更、次の出発）
      → 経路詳細（各区間、途中駅、取得済み番線、保存、共有）
        → この経路を使う → 今の案内準備
```

候補カード全体がタップ対象。既存の App Back／History Back／指に追従する Swipe Back、タブごとの Stack、スクロール・入力・選択・地図位置の保存を利用。新しい画面をホームに縦積みしない。烏丸線・近鉄・直通・K/B境界・全バス／停留所・北3・前方／反対列車・Realtime・時刻表・折返し・運賃／定期・通知・GPS・Dark Mode・Reduce Motion等は維持する。
